# 初回加算の自動算定 — 現況と提案

user 要望 (2026-09-03): 「訪問介護の初回加算が、**要件を確認して自動で算定する**ことを
提案してもらえると助かる」

---

## 1. 現況 — 提案の仕組みは既にある。だが ★ ほぼ全員に出る

実装は 2 か所。**どちらも「候補」バッジを出すだけで、自動チェックはしない。**

| | ファイル | 判定材料 |
|---|---|---|
| 訪問介護 | `billing-visit/kaigo-seikyu/kaigo-seikyu-content.tsx:425` | `kaigo_visit_schedule` の `status='completed'` |
| 居宅 | `billing/seikyu/_kojin-settei.tsx:261` | `kaigo_care_support_claims` のレセプト |

判定はどちらも同じ形:

```
過去 2 ヶ月 (前々月・前月) に 1 件も無ければ → 「新規」= 初回加算の候補
```

### ★ 欠陥: 「その人に無い」と「そもそも誰にも無い」を区別していない

実測 (2026-09-03 / service_role):

```
kaigo_visit_schedule  status='completed'        kaigo_care_support_claims
  2026-03        0 件                             2026-03        0 件
  2026-04        0 件                             2026-04        0 件
  2026-05        4 件                             2026-05        0 件
  2026-06   36,723 件                             2026-06    2,806 件
  2026-07    2,890 件                             2026-07    2,791 件
  2026-08      762 件                             2026-08        0 件
```

**2026-06 を請求しようとすると、過去 2 ヶ月 = 2026-04 と 2026-05。**
訪問介護は 4 件・居宅は 0 件しか無い。
→ ★ **ほぼ全利用者が「初回加算 候補」になる。**居宅は 2,806 名 **全員**。

的中率 3.7% はロジックの精度ではなく、**入力データが 1 ヶ月ぶんしか無いこと**が原因。

⚠ **ロジックを直しても的中率は上がらない。**上がるのは
「**判定できないときに黙って新規と言わなくなる**」ことだけ。

---

## 2. 提案 — 3 段で入れる

### 段1 (すぐ入る・データ待ちなし) ★ 分母を見て fail-closed にする

いま `count === 0` を「新規」と読んでいる。**その窓に事業所全体で何件あるか**を
同時に数え、0 なら「判定できない」を出す。

```
窓の全体件数 = 0   → ★「判定不能」 (グレー)。★ 候補バッジを出さない
窓の全体件数 > 0
  └ その人が 0 件 → 「候補」 (現行どおり)
  └ その人が有り → 出さない
```

⚠ **これは否定推論の禁止そのもの** (memory `feedback_negative_inference_system_label`)。
「実績が無い = 新規」は、**材料が無いときに外れた側を確定させている**。

⚠ 現行は取得エラー時に `setShokaiCandidate(false)` にしていて、これは正しい
(候補を出さない側に倒れる)。**同じ倒し方をデータ欠損にも広げる**だけ。

### 段2 (要データ) ★ 過去 2 ヶ月の実績を入れる

`SESSION_START.md` の「次回まとめて出すもの #10」がそのまま前提。

```
2026-04 / 2026-05 の MEISAI + 介護請求(明細付)_一覧
→ 入れば 段1 の「判定不能」が自然に解消し、判定が実際に効き始める
→ ★ 経営分析の前月比 (いま「新規2,270名 / 終了2,075名」) も同時に直る
```

### 段3 (要検討) ★ 実績以外の材料を足す

実績だけで「新規」を決めるのは、そもそも要件と一致していない。

```
初回加算の算定要件 (訪問介護 114001 / 居宅 434001)
  ・新規に訪問介護計画を作成した利用者
  ・★ 過去 2 ヶ月以上サービス提供が無い場合も「新規」扱い
  ・★ 要介護度が要支援 → 要介護 に変わった場合も算定できる
```

→ 実績だけでなく **① 認定の開始日 ② 契約日 ③ 要支援→要介護の変更** を材料にできる。
特に ③ は `client_insurance_records` から機械的に取れる。

⚠ ただし **③ を今すぐ入れると誤検出が増える**恐れがある。認定データは
「認定の重複マージ 122 件」が未処理で、**同着で採用行が決まらない問題を直した直後**。
★ 段2 の後に、実データで的中率を測ってから入れること。

---

## 3. やらないこと

⚠ **自動でチェックを入れる (= 自動算定) はしない。**現行が「候補バッジのみ」なのは
正しい設計。初回加算は 300 単位で、誤算定すると返戻・過誤申立になる。

```
提案 = 候補を出す         ★ 人が確認して付ける
自動算定 = 勝手に付ける   ⚠ 材料が不完全なうちは危険
```

user 要望の「要件を確認して自動で算定する」は、**段2 で材料が揃い、段3 で要件を
機械的に判定できるようになってから**。それまでは ★ 候補の精度を上げる。

---

## 4. 検証のしかた

段1 を入れたら、★ 前後で「候補の件数」を比べるだけでは不十分 (規則 3-2)。

```
① 2026-06 で「判定不能」が ★ 全員に出ること (窓が空なので当然そうなるべき)
② 2026-07 で「候補」が ★ 少数に絞られること (窓 = 05/06 で 06 に 2,806 件ある)
③ ★ 負のコントロール: 窓に 1 件だけ入れて、判定不能 → 候補 に切り替わること
```

②が本番の的中率に相当する。**①だけ見て「直った」と言わないこと** (規則 3-19)。
